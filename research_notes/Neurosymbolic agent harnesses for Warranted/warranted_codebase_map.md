# Warranted codebase map: guarantees, gaps, and neurosymbolic extension points

Scope: the local repository at `/home/user/warranted` (main at `00e9f70`, package version 0.2.0, research date 2026-10-09). Every source below is a repository file path (with section heading); links are relative to the repo root. "Implemented/Tested" means code plus a negative-case test exists; "Planned/Proposed" means only documentation exists.

## Q1. What is Warranted: purpose, design philosophy, core concepts

### Takeaway
Warranted is a domain-independent, single-host Python harness in which an LLM worker explores freely in a contained shell while trusted symbolic host machinery (an append-only SQLite evidence ledger, declared dependencies, deterministic checkers, and Lean verification) alone decides what counts as accepted knowledge. Its philosophy is "make the world legible, give the model room to explore, and be precise about what counts as established knowledge", and it explicitly calls itself a neurosymbolic harness.

### Cited Findings
- Self-description: "a neurosymbolic harness for agents doing long, interdependent work. A language-model worker explores freely in a contained shell. The host keeps an authoritative evidence ledger, tracks what each conclusion depends on, and accepts work only when the independent checks its contract requires pass: deterministic checkers, plus Lean proofs where the contract asks for them." — [README.md, intro](README.md)
- Working principle: "make the world legible, give the model room to explore, and be precise about what counts as established knowledge." — [README.md, intro](README.md)
- Purpose: pair "a neural worker, which proposes plans, programs, and proofs, with symbolic machinery the worker cannot override: a versioned ledger, declared dependencies, deterministic checkers, and Lean verification"; when an input changes, "revisit the affected work instead of reconstructing the entire argument from prose." — [docs/design.md, Purpose](docs/design.md)
- Two hypotheses, both untested: (1) checked, reusable knowledge improves completion and recovery; (2) Dream-RSI-inspired search scheduling adds further gains. "Lean must earn its cost over executable models and ordinary checks." — [docs/design.md, Purpose](docs/design.md)
- The owner's stated aim (2026-10-03) for M9: "a general-purpose neurosymbolic harness: a model proposes, and symbolic machinery (tests, solvers, proof kernels, measurements) decides what is accepted." — [docs/proposals/general-purpose-harness.md, intro](docs/proposals/general-purpose-harness.md)
- Responsibility boundaries (not services): Host controller (permissions, authoritative writes, budgets, recovery, acceptance); Evidence ledger (SQLite + SHA-256 artifact files); Worker (mini-swe-agent 2.4.6, shell+files in rootless Podman); Workflow runner (LangGraph 1.2.11 + SQLite checkpointer); Domain environment; Independent checker ("Deterministic fixture checkers and Lean verification; no model-judgment gates"); Exploration policy ("One fixed serial policy; no replay or evolved policy"). — [docs/design.md, Boundaries and ownership](docs/design.md)
- Three distinct graphs that must not substitute for each other: the workflow execution/checkpoint graph, the dependency graph between knowledge artifacts, and the discovery tree of investigation attempts. — [docs/design.md, Durable knowledge](docs/design.md)
- Record kinds: observations (raw results + source operation + input versions + environment + time; "what a source reported, not infallible truth"), artifacts (digests + dependencies), claims (statements, assumptions, scope, supporting/conflicting evidence), validation receipts (checker identity/version, target, artifact, input, environment, method, outcome; "Workers cannot author accepted receipts"), operations (stable IDs, reservations, usage), decisions/policy versions. — [docs/design.md, Durable knowledge](docs/design.md)
- Rules vs gates: "A rule allows a recorded, scoped exception. A gate permits a protected transition only after designated, independently checkable evidence is present. Gate definitions include their applicability predicate, exact target, evidence requirements, and checker. Unknown kinds, unknown applicability, missing evidence, and checker failure do not default to permission." — [docs/design.md, Rules, gates, and verification](docs/design.md)
- "Formalisation is progressive. Begin with executable models and regression checks; introduce Lean for obligations whose reuse or failure cost makes proofs worthwhile." — [docs/design.md, Rules, gates, and verification](docs/design.md)
- Three assessments kept distinct: valid proof of a proposition; whether premises and implementation correspondence support its current use; whether the candidate satisfies the task's acceptance obligations. "A valid proof cannot override a failed behavioral check." Acceptance "does not certify that the contract captures every user need." — [docs/design.md, Intent, contracts, and acceptance](docs/design.md)
- Contract review heuristic: "what implementation would satisfy it but clearly disappoint the user?", including "empty or degenerate behavior that makes a property vacuously true." Candidate-generated tests "cannot replace independent acceptance checks." — [docs/design.md, Intent, contracts, and acceptance](docs/design.md)
- Implementation style: smallest complete slice; "avoid a custom agent loop, workflow engine, ORM, or plugin framework without a demonstrated need"; ledger records "must not become a mandatory sequence of model-facing tools"; "a command wrapper alone is not isolation"; preserve distinct outcomes "rejected, unproved, unsupported, unknown, and infrastructure failure". — [AGENTS.md, Implementation style](AGENTS.md)
- Eight invariants (raw evidence/origin; validity vs applicability; rules vs gates/no opt-out; host checks gates at the protected transition; usage/unknown outcomes survive restart; replay reveals only recorded outcomes; split separation and failure/cost reporting; a pass establishes only its stated scope). — [AGENTS.md, Invariants to preserve](AGENTS.md)
- Domain-independence constraint: "Do not put another project's tool names, validator rules, state formats, budgets, or acceptance semantics into the core; domain behavior enters through the checker, job, and worker-image interfaces. Host-mediated operations need a reviewed design before any implementation." — [AGENTS.md, Working on Warranted](AGENTS.md)
- ReSchema is the first external consumer; "Warranted never depends on ReSchema." M7 constraint: "the core contains no reverse-engineering concepts. Traces, canonicalisation, emulation, and fuzzing stay in ReSchema behind the checker, job, and worker-image interfaces." — [AGENTS.md](AGENTS.md); [docs/roadmap.md, M7](docs/roadmap.md)
- Scope: "a local host, one ledger writer, bounded workers in rootless containers, and two controlled task families. There is no distributed coordination, unrestricted self-modification, weight training, universal ontology, or real-world write." — [docs/design.md, Scope and provisional choices](docs/design.md)
- Size: `src/warranted` ~9.6k lines of Python (largest: `_tasks.py` 2368, `_ledger.py` 1079); ~507 test functions across 47 test files; runtime deps only langgraph 1.2.11, langgraph-checkpoint-sqlite 3.1.1, litellm 1.104.0, mini-swe-agent 2.4.6; Apache-2.0. — [pyproject.toml](pyproject.toml); `wc`/`grep` over [src/warranted](src/warranted) and [tests](tests)

### Inferences
- Warranted already occupies the "LLM proposes / symbolic verifier disposes" (propose-verify, LLM-modulo-style) architecture; neurosymbolic recommendations should therefore target its *evidence semantics* (what kind of warrant a pass carries, how dependencies and applicability are computed, how contracts are formalised) rather than introducing the basic propose-check loop.
- The design is explicitly anti-framework and anti-tool-proliferation; recommendations that add model-facing tools, a DSL the worker must use, or a heavy reasoning engine in the core would conflict with AGENTS.md. Symbolic engines fit best as checker jobs, worker-image tools, or host-side trusted code.

### Gaps
- The intended long-term ontology of "claims" (e.g., whether claims ever compose logically) is not specified; docs say parent edges "do not prove an inference from parent statements" ([docs/reference/claims-and-acceptance.md, Claims](docs/reference/claims-and-acceptance.md)), so no inference calculus over claims exists or is planned.

## Q2. Implemented and tested vs planned; enforcement status per invariant

### Takeaway
Implemented (tested, local, single trusted writer): ledger with immutable observations/receipts/reservations/unknown-outcome blocking; claims with separate validation vs applicability; acceptance gates with no opt-out; contained worker (mini-swe-agent in rootless Podman); checker jobs; host-mediated operations; Lean verification with Comparator/Landrun and durable proof receipts; task layer (Project/TaskSpec/Domain/Checker/Verdict), scoped memory, duplicate guard, revisions, campaigns with splits, CLI, three model adapters. Not built: replay (M6), optimisers, model judges (M3a), trust bases/measurements/solvers/strategies/chains/consolidation (M9), measured A–E comparison, live-model completion of any full task sequence.

### Cited Findings
- Milestone status: M0–M4 complete within fixture scopes; M5 fixtures complete, comparison deferred; M7 "Next" (most checkboxes ticked; Public API and Token budgets unticked); M8 planned; M9 proposed; M6 (Dream-RSI) and M3a (Jev) deferred. "'Complete' ... does not extend to live models, untrusted hosts, or tasks outside the fixtures." — [docs/roadmap.md, table](docs/roadmap.md)
- M4 delivered: "pinned Lean, Comparator, and Landrun check a reviewed uniqueness target, reject weakened statements, `sorryAx`, and unapproved axioms, and replay the proof in the kernel"; limits: "proofs are fixed proposals. Model proof search and a cost comparison against executable checks have not been run." — [docs/roadmap.md, M4](docs/roadmap.md)
- Live-model evidence: no live run has completed the revision+restart sequence; no A–E comparison run. In corrected controls (local qwen3.8:27b, migration condition A, 12 runs): 7 accepted, 2 rejected, 3 unsubmitted; "Every retained final program passes the original five checks ... Only two reject the separate boolean-version case." — [README.md, What live-model runs have shown](README.md); [docs/experiments/2026-09-25-corrected-submission-controls.md](docs/experiments/2026-09-25-corrected-submission-controls.md)
- Enforcement audit method: tiers Tested / Partial / Documented / Not built, adapted from Clauderizer's enforcement ladder; audited 2026-10-03 at `f588371`. Two standing trust assumptions: the host process writing the ledger is trusted (`Ledger.record` accepts caller's `Origin`), and workers never hold the ledger. — [docs/reference/enforcement.md, intro and Tiers](docs/reference/enforcement.md)
- Invariant 1 (raw evidence keeps version and origin): all four clauses **Tested** — versioned/never-repaired bytes; origin retention (`Ledger._check_origin` requires cited inputs match a snapshot or committed observation channel); agent text cannot forge a tool result (`test_host_operations.py::test_worker_output_cannot_forge_or_trigger_host_results`); cannot forge an acceptance receipt (`test_re_fixture.py::test_forged_verdicts_receipts_and_tiers_establish_nothing`, `test_proof_checks.py::test_a_forged_verdict_file_in_the_workspace_is_ignored`). — [docs/reference/enforcement.md, §1](docs/reference/enforcement.md)
- Invariant 2 (validity vs applicability): "stale premise does not turn a valid result false" **Tested** (`Claims.assess` returns validation and applicability separately); "superseded premises block dependent applications" **Partial** — task-layer memory and acceptance block, but host-kit `Claims.assess` "only reports `stale`, and callers must act on it." — [docs/reference/enforcement.md, §2](docs/reference/enforcement.md)
- Invariant 3 (gates, no opt-out, unknowns never pass): rules-have-exceptions **Partial** (task layer has no rules; every required check is a gate); gates-no-opt-out, independent checking, only-real-`Verdict`-counts, unknown kinds/applicability never succeed, missing/stale evidence never succeeds — all **Tested**. — [docs/reference/enforcement.md, §3](docs/reference/enforcement.md)
- Invariant 4 (host checks gates at protected transition): exact target/inputs/environment **Tested**; current dependencies **Partial** (task layer pins contract per run; a run in progress in another process continues under its pinned contract); workers cannot weaken target/checker/budget **Partial** (isolation tested only under `container` marker); "Optimisers cannot weaken them" **Not built** ("No optimiser exists"). — [docs/reference/enforcement.md, §4](docs/reference/enforcement.md)
- Invariant 5 (usage/unknowns survive restart): all clauses **Tested**, including litellm single-dispatch with retries off and lost replies kept unknown. Caveat: reconciling an op declaring no external effect "relies on the domain's own effect declaration." — [docs/reference/enforcement.md, §5](docs/reference/enforcement.md)
- Invariant 6 (replay): replay **Not built** (no engine; M6); "Missing history is unsupported" **Tested, for exported history** (`capture_history` refuses missing episodes). — [docs/reference/enforcement.md, §6](docs/reference/enforcement.md)
- Invariant 7 (splits/failures/costs): provenance separation **Partial** (memory only); lineage **Partial** (lineage = task ID; "a copy under a new ID is not detected"); failed attempts reported **Partial**; optimisation cost **Not built**. — [docs/reference/enforcement.md, §7](docs/reference/enforcement.md)
- Invariant 8 (a pass establishes only its stated scope): **Partial** — decisions bind target/policy/revision/check digests, but "That a pass does not establish intent or whole-task success is documented, not executable"; spec binding until authorised revision **Partial** (owner not verified); failed obligations preserved **Tested**; "Known gaps are preserved" **Documented** only. — [docs/reference/enforcement.md, §8](docs/reference/enforcement.md)
- Audit's open gaps: host-kit staleness reported not enforced; rejected runs and cost totals in campaign reports untested. — [docs/reference/enforcement.md, Known gaps found by this audit](docs/reference/enforcement.md)
- Durability limit: tests establish recovery from process termination, "not ... from power loss or disk loss"; storage format v3, no migration. — [README.md, Local evidence API](README.md)
- Not provided anywhere: concurrent writers, remote owner authentication, external-effect authorisation, replay, second proof kernel. — [docs/reference/claims-and-acceptance.md, Guarantees and limits](docs/reference/claims-and-acceptance.md); [docs/reference/proof-verification.md, Limits](docs/reference/proof-verification.md)

### Inferences
- The strongest implemented guarantees are integrity/provenance/recovery properties (a "trusted computing base" story), not semantic correctness; invariant 8 (scope of a pass vs intent) is the weakest-enforced and the most natural target for neurosymbolic work (typed warrants, specification-adequacy checks).
- "Known gaps are preserved" being Documented-only and trust basis absent (see Q3) mean an assurance-case/argument layer would fill a real, acknowledged hole.

### Gaps
- No measured data exists on whether any symbolic component (dependency tracking, Lean) helps task success; all demonstrations are scripted or fixed-proposal ([README.md, What has been demonstrated](README.md)).

## Q3. Interfaces and representations: checker, job, worker image, gates, evidence, receipts, proofs/premises, applicability, replay, budgets

### Takeaway
Domain behaviour enters through a `Domain` protocol (name, version, pinned `worker_image`, `checkers`, optional `sources`, optional `operations`); a `Checker.check(CheckContext) -> Verdict` with a closed `VerdictStatus` enum (passed/rejected/unproved/unsupported/infrastructure_failure); contained `run_job` jobs; host-recorded `draw_seed`; and `CheckContext.verify` for Lean. Acceptance is the conjunction of all required checks; there is no numeric verdict, no trust-basis label, and no solver-specific interface yet.

### Cited Findings
- `Domain` protocol fields (code): `name`, `version`, `worker_image`, `checkers: Mapping[str, Checker]`, optional `sources`, optional `operations: Mapping[str, Operation]`. Identity digest covers class source files of domain/checkers/operations plus declared `sources` and the installed Warranted package digest; "Imports are not followed automatically, so undeclared code is not pinned." — [src/warranted/_tasks.py, `class Domain`, `_source_files`](src/warranted/_tasks.py); [docs/proposals/m7-harness-api.md, Answers to open questions 3 and 4](docs/proposals/m7-harness-api.md)
- `Checker` protocol: trusted host code; `version: str`; `check(ctx) -> Verdict`; optional `isolated = True` (isolated checks run in the run's ledger scope, others in the root scope, "where an unknown outcome blocks every run"). Any non-`Verdict` return, "including a subclass or an object with the same attributes, is recorded as an infrastructure failure." — [src/warranted/_tasks.py, `class Checker`](src/warranted/_tasks.py)
- `Verdict(status, feedback=None, host_only=None, facts=())`; feedback ≤ 64 KiB (`FEEDBACK_LIMIT`; oversized = checker fault, not truncation); facts strict JSON (≤16 facts / 16 KiB). — [src/warranted/_tasks.py, `class Verdict`](src/warranted/_tasks.py); [docs/proposals/m7-harness-api.md, Answers to open questions 3 and 4](docs/proposals/m7-harness-api.md); [docs/proposals/m7-scoped-memory.md, Two sources, three tiers](docs/proposals/m7-scoped-memory.md)
- `VerdictStatus` = PASSED, REJECTED, UNPROVED ("could not be established within limits; fails the gate"), UNSUPPORTED, INFRASTRUCTURE_FAILURE. `RunOutcome` = accepted, rejected, incomplete, unknown, unsupported, infrastructure_failure (CLI exit codes 0,1,1/2,3,4,5). — [src/warranted/_tasks.py](src/warranted/_tasks.py); [docs/proposals/m7-harness-api.md, Decisions so far #11 and Run lifecycle](docs/proposals/m7-harness-api.md)
- `CheckContext`: read-only `candidate` (captured bytes), `inputs`, `private` (never mounted for worker); `draw_seed()` recorded as host-only evidence; `run_job(...)`; `verify(target, source)` calls the project verifier and logs target/challenge digest/source digest/status/axioms/identity as host-only evidence. — [src/warranted/_tasks.py, `class CheckContext`](src/warranted/_tasks.py)
- Jobs: `PodmanJobs().run(image, argv, files, stdin, timeout_seconds, limits)` → `JobResult(returncode, stdout, stderr, timed_out, truncated)`; image pinned by digest or local ID; no network, no host mounts, read-only root, UID 1000, no caps; `JobLimits` up to 8 GiB / 1024 pids / 4 GiB scratch / 8 CPUs; runner `identity` bound into project identity; job output is "that program's claim about itself, never ... host evidence about anything else." Jobs are recorded inside their check operation, not as separate ledger operations. — [docs/reference/worker-and-containment.md, Checker jobs](docs/reference/worker-and-containment.md); [docs/proposals/m7-harness-api.md, Answers to open questions 1, 5, and 7](docs/proposals/m7-harness-api.md)
- Worker images: domain supplies pinned `worker_image` with its own tools; "The image adds tools inside the container; it does not widen what the container can reach." CI exercises one domain image adding a tool. — [docs/roadmap.md, M7 Domain worker images](docs/roadmap.md)
- Worker convention: `/work/task.md`, `/work/inputs/`, `/work/context/`, `/work/feedback/NNN.json`, `/work/submission/`, `notes.json` (unverified), a `submit` helper; follow-on episodes receive restored workspace + feedback files, not the prior conversation. — [docs/proposals/m7-harness-api.md, Worker convention; Answers to open questions 1, 5, and 7](docs/proposals/m7-harness-api.md)
- Host-mediated operations: `Operation` protocol with `version`, `effect: "none"|"external"`, `shared`, `reusable` (only if deterministic and effect-free), `inputs`, `parse`, `reservation`, `execute`, optional `reconcile`; `OperationResult(outcome, usage, raw, shown ≤64 KiB, files)`. Requests travel via the existing journaled command channel; completed operations are host evidence citable by operation ID. — [docs/proposals/m7-host-operations.md, Domains declare their operations; Results as evidence](docs/proposals/m7-host-operations.md)
- Acceptance (host kit): JSON policy with `requirements` each `{"kind": "gate"|"rule", "check", "field"}`; checker `result.json` must have exactly the policy's boolean fields; overall status precedence `unsupported > infrastructure_failure > unknown > missing > stale > rejected`, else `accepted`; every requirement's status retained; decisions are uncharged ledger operations binding target, policy, revision, checker request digests. In the task layer "each required check becomes a gate on a `passed` field." — [docs/reference/claims-and-acceptance.md, Acceptance / Policy format / Checker evidence](docs/reference/claims-and-acceptance.md); [docs/proposals/m7-harness-api.md, Prototype findings Slice 1](docs/proposals/m7-harness-api.md)
- Claims: `claims.record(statement, target, assumptions, parents, validation, complete)`; `claims.assess(claim, current)` returns separate `validation` (unproved/missing/unknown/unsupported/infrastructure_failure/passed/rejected) and `applicability` (current/stale/unknown); staleness propagates via parent edges; "`current` establishes version agreement, not that an assumption is true. Parent edges ... do not prove an inference from parent statements." Dependencies "are declared by the trusted host; they are not inferred." — [docs/reference/claims-and-acceptance.md, Claims](docs/reference/claims-and-acceptance.md); [docs/design.md, Durable knowledge](docs/design.md)
- Proofs: `ProofTarget(path, theorem)` is domain-owned; `LeanProof(target, source="Solution.lean", premises=None, correspondence=None, isolated=False)`; premises (applicability about inputs; failure → UNSUPPORTED) and correspondence (candidate matches the theorem's model; failure → REJECTED) are trusted `fn(ctx) -> {name: bool}`; "Applicability wins"; non-boolean/raising → checker fault. — [docs/proposals/m7-proofs.md, Interface; Premises and correspondence](docs/proposals/m7-proofs.md); [src/warranted/_proof_checks.py, `LeanProof.check`](src/warranted/_proof_checks.py)
- Lean verifier: Lean 4.34.0, Comparator (theorem comparison, axiom traversal, kernel replay), lean4export, Landrun; axioms allowed exactly `propext` and `Quot.sound`; challenges import only `Init` (no Mathlib); no definition holes; outcomes proved/rejected/unproved/unsupported/infrastructure_failure; "No status other than `proved` shows the target theorem false"; one `proof` unit per attempt; "no second kernel implementation is used." — [docs/reference/proof-verification.md, Targets and axiom policy; Tools, trust, and attribution; Outcomes](docs/reference/proof-verification.md)
- Proof application rule: supported "only by passing, current evidence for the theorem, every application premise ..., and a correspondence check showing the exact candidate's output matches the formal model." — [docs/reference/proof-verification.md, Claims and applications](docs/reference/proof-verification.md)
- Correspondence is checked on development inputs only (e.g., by running candidate output vs model variant), not proved. — [docs/experiments/evaluation-design.md, Specification and behavioral failures](docs/experiments/evaluation-design.md)
- Scoped memory: tiers `verified` (checker facts from accepted submission), `promoted` (worker notes from accepted submission), else withheld; each fact is a claim with assumptions `domain` and `file/<name>`; one immutable `memory.json` snapshot per run; stale/unknown entries withheld. — [docs/proposals/m7-scoped-memory.md, Proposal](docs/proposals/m7-scoped-memory.md)
- Budgets: task budgets (submissions, checks); run budgets (model calls, shell commands, tokens, operation units) via ledger scopes with caps under project totals; reservations before dispatch; token-budget enforcement implemented but "no adapter reserves tokens" until a model is verified by measurement. — [docs/proposals/m7-harness-api.md, Budgets and the duplicate guard](docs/proposals/m7-harness-api.md); [docs/roadmap.md, M7 Token budgets](docs/roadmap.md)
- Replay: not built; host-ops design says replay "returns recorded request results by operation ID ... A request with no recorded result is unsupported"; LangGraph time travel is explicitly not Warranted replay. — [docs/proposals/m7-host-operations.md, Replay](docs/proposals/m7-host-operations.md); [docs/reference/worker-and-containment.md, Limits](docs/reference/worker-and-containment.md)
- A–E context layers: A workspace+notes; B +queryable observation/action history; C +executable models and regression checks; D +dependency/applicability reports; E +Lean proof workflow; host-selected, frozen as evidence, fail-closed. — [docs/reference/contexts.md, Selecting support](docs/reference/contexts.md); [docs/experiments/evaluation-design.md, Knowledge-workflow conditions](docs/experiments/evaluation-design.md)

### Inferences
- The `Checker` protocol is already general enough to host any symbolic engine (SMT, model checker, Datalog, abstract interpreter, second proof kernel) inside `run_job`; what is missing is a way for the verdict to *declare what kind of warrant* it gives (N6) and to return certificates/measurements as typed evidence.
- Premises and correspondence are boolean Python callbacks; they are the obvious seam where formal correspondence (e.g., refinement proofs, translation validation, property-based or SMT-backed equivalence checks) could replace development-input sampling.
- Claims' dependency graph is a hand-declared DAG with version-equality applicability — structurally a truth-maintenance system (justification-based) without inference; a neurosymbolic recommendation could add logic-based dependency inference while keeping host-declared edges authoritative.

### Gaps
- The exact on-disk SQLite schema was not inspected here beyond docs ([docs/reference/evidence-ledger.md](docs/reference/evidence-ledger.md) headings: Storage, Value types, Operation identity and recovery, Scopes, Permitted exports).

## Q5. Open roadmap items, known gaps, design questions, and neurosymbolic extension points

### Takeaway
The M9 "general-purpose neurosymbolic harness" proposal (N1–N11) is the main open frontier and already sketches several neurosymbolic extensions (trust bases, solver-checked `unsat`, certificates, per-task Lean targets with Mathlib, strategies for multi-candidate search, chains of accepted results, checked consolidation). The clearest under-specified seams are: typed warrant/trust basis on verdicts; formal correspondence instead of sampled correspondence; specification-adequacy (invariant 8, only Documented); dependency inference beyond host-declared edges; model judges as gates (M3a); replay and policy evolution under invariants (M6); and an optimiser that cannot weaken gates (Not built).

### Inferences (candidate extension points for neurosymbolic ideas; each mapped to an existing seam)
1. **Typed warrants / trust bases (N6) as a mini assurance-case layer**: extend `Verdict` with a declared basis and attach to decisions; a GSN-style or eliminative-argument record could make invariant 8 executable ("this acceptance rests on: kernel proof of P under axioms A + example-basis check E + measurement M; known gaps G"). Seam: `Verdict`, acceptance decision record, `campaign report`. Must remain unordered per N6.
2. **Certificate-producing solvers (proof-carrying evidence)**: N7 already names Alethe/Carcara; generalise to LRAT/DRAT for SAT (cake_lpr/drat-trim), SMT proof reconstruction into Lean (e.g., lean-smt/`lean-auto`-style), so `solver` basis can be upgraded to `certificate` or `kernel`. Seam: checker jobs in pinned images; no core change except basis labels.
3. **Formal correspondence instead of sampled correspondence**: `LeanProof.correspondence` is Python boolean code run on development inputs; refinement/translation-validation (e.g., proving the Python/C candidate refines the Lean model via extraction, symbolic execution, or SMT-based equivalence over bounded domains) would close the "proof of a Lean function does not verify a separate implementation" gap ([docs/design.md, Rules, gates, and verification](docs/design.md)). Seam: `correspondence` callbacks + `run_job`.
4. **Specification-adequacy checking (invariant 8, Documented only)**: vacuity checks, mutation testing of contracts, and LLM-generated "disappointing implementations" checked against the formal target (the design's own review heuristic) could be automated as a contract-review job whose output is a recorded known-gap list, never a gate waiver. Seam: contract revisions (`Project.revise`), intent records (`examples/m2/fixture/intent.json`).
5. **Autoformalisation with owner approval**: N5's per-task targets come from pinned task inputs; an LLM can propose Lean/SMT formalisations of requirements, but per design a "generated interpretation ... is a proposal, not authority"; owner approval via revisions. Seam: `Revision`, `ProofTarget`.
6. **Dependency inference / truth maintenance**: claims are a justification graph with version-equality applicability and conservative unknowns; static analysis or provenance capture (e.g., syscall/file-read tracing inside jobs, Datalog provenance) could *propose* dependency edges that the host then declares, reducing `unknown`. Must not let inferred edges silently replace declared ones.
7. **Formal policies for gates and budgets**: acceptance policy is a small JSON format; a declarative policy language (Cedar/Rego/Datalog) could express applicability predicates and gate composition with analysable semantics, but AGENTS.md disfavours new frameworks without demonstrated need.
8. **Search/strategy with symbolic filtering (N3)**: ARC/Lean sample-and-filter, CEGIS-style refinement loops using counterexamples from checker feedback, neural proof search with the existing verifier as reward—all must keep host-owned checks and budgets.
9. **Library learning / consolidation (N11)**: DreamCoder-style abstraction with kernel-checked lemmas and no-interference checks; already proposed, so recommendations should focus on concrete mechanisms (e.g., LEGO-Prover/lemma libraries, verified helper extraction).
10. **Model judges as calibrated gates (M3a)**: only for statistical criteria, with abstention as blocking; neurosymbolic angle is to constrain judges with typed rubrics/structured outputs and to measure false-accept rate.
11. **ReSchema-specific (stays in ReSchema)**: symbolic execution/emulation, decompilation equivalence, differential fuzzing — enter only as checkers/jobs/worker images; any recommendation must keep RE vocabulary out of core.
